# History paging

The workspace keeps a retention window of history; older flights, problem reports and work orders load page by page ([ADR-0013](adr/0013-history-retention-window.md), decision D3, finding SZ-1). This page holds the window's rule, the read counts it is measured against, and every lookup by uuid the window can break, with what each one should do.

Status, 20 Nov 2026: the rule exists in the domain and is tested (`src/domain/retention.ts`), the baseline is recorded (`convex/historyCost.test.ts`), every row the window will index carries its derived columns, with a backfill for older rows (S2, below), the saves load a bounded working set instead of whole history, with numbering read from `recordNumbers` (S3, below), the board and the cost report total spending from `costLedger` (S4, below), the paged queries are in the server, the `Backend` interface and the demo (S5, below), and the screens and whole-history features read them (S6, below). The workspace still loads full history until S7 turns the window on.

## The window

`retainedSnapshot(snapshot, now)` keeps, from a full scoped snapshot:

| Records                       | Kept in the workspace                                                                                                                                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Flights                       | Held for review, or started or submitted in the last 183 days (`FLIGHT_RETENTION_DAYS`, H1)                                                                                                                              |
| Problem reports               | Open (deferred ones included), or created, resolved or deferred in the last 90 days (`RETENTION_DAYS`)                                                                                                                   |
| Work orders                   | Open; holding an open job card; opened, closed, revised, corrected, or with a job card or cost entry changed in the last 90 days; or among the 5 latest completed on their aircraft, ties kept (the owner portal's list) |
| Job cards, archived job cards | With their work order; templates and cards of an order not in the snapshot always                                                                                                                                        |
| Cost records                  | A work order's with its order; budgets and the labor rate always                                                                                                                                                         |
| Everything else               | Complete: inspections, ADs, management records, checklists, templates, parts requests, purchase orders and flight plans (H5); the change log keeps its 250 rows                                                          |

The cutoff is the start of the UTC day the window opens on (`retentionCutoff`). Rounding down only widens the window and holds one cutoff for a whole day, so a record crossing it appears both in an older copy of the workspace and in the newer history pages, never in neither.

`historyPage(snapshot, request, now)` is the paging oracle: the next page of what the window leaves out, for flights (optionally one aircraft and one status, H2), problem reports or work orders, newest first in the order below. A work order page carries the order's job cards, archived job cards and cost record, and every page the members its rows name (pilots, copilots, reporters and resolvers) for their names. The cursor is a position (sort key and uuid), not an offset, so it stays valid when newer records arrive. An aircraft the snapshot does not list is refused with "History not found.", as one that does not exist. The demo pages with it, and the server's paged queries are tested against it.

### The order of each list

Each list's order is one index range per aircraft on the server, so a page reads only the rows it returns and the rows the window keeps between them (S5 resolved correction 4 this way, changing the oracle rather than adding a column):

| List            | Newest first by                                                        | Index range per readable aircraft                                                 |
| --------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Flights         | Start instant (`startedAt`)                                            | `started`: `[aircraftUuid, startedAt, uuid]`, below the flight cutoff             |
| Problem reports | Creation time                                                          | `status`: `[aircraftUuid, status, createdAt, uuid]`, resolved only                |
| Work orders     | Completion date; a cancelled order without one after every dated order | `status`: `[aircraftUuid, status, completionDate, uuid]`, completed and cancelled |

- **Equal keys by uuid, highest first.** The three indexes end in `uuid`, so the server reads ties in the oracle's order and a cursor resumes inside a tie. Convex otherwise breaks ties by creation time, which a demo or a backup restore cannot reproduce. Adding a field to an index needs no backfill: Convex builds the index from stored fields.
- **Flights by instant, not by the recorded text.** The text keeps the pilot's offset, so it does not sort by instant across offsets; `startedAt` is that text in milliseconds. The Flight log sorted by the text, which is the same order whenever a program's flights share an offset; since S6 it sorts by instant.
- **Work orders by completion date, not opening.** No column holds `recordedAt`, and one would need another backfill. Every order the window leaves out is closed, so its history is closed work, which the owner portal and the paper check already list by completion date. Completed orders always have one; a cancelled order may not (""), and sorts last. `closedAt` was the other candidate, but it is absent on every open order and on a cancelled order without dates, so its range would mix open orders into history; the `status` index never reads an open order. Since S6 the Work orders screen lists closed orders by completion date, under the open ones (newest opened first).
- **No older row sorts before its list's start** (`historyStart`): a flight started, report created or order completed on or after the cutoff's day is never older history, so each range starts there.

## Derived columns and tables (S2)

The window's queries need indexes on fields that live inside a record's JSON payload, so each row copies those fields into columns of its own. `encode` in `convex/collections.ts` sets them on every write of a payload row, and `flightColumns` on every write of a flight's start; decoding never returns them, so the workspace, the change log and the readable records copy are unchanged. Every column is optional, so rows written before S2 stay valid until the backfill fills them. The paged queries (S5) read the columns; the bounded saves (S3) and the ledger (S4) read the new tables.

| Table              | Derived columns                                                                                                                                                                                                                                 | New indexes                                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Flights            | `startedAt`: the start time in milliseconds, since the stored text keeps the pilot's offset and does not sort by instant                                                                                                                        | `[aircraftUuid, startedAt, uuid]`, `[aircraftUuid, submittedAt]`, `[aircraftUuid, status]`                       |
| Problem reports    | None: the fields are columns already                                                                                                                                                                                                            | `[aircraftUuid, status, createdAt, uuid]`, `[aircraftUuid, resolvedAt]`                                          |
| Work orders        | `status`; `completionDate`; `numberKey` (the number in lower case, as the uniqueness check compares it); once closed, `closedAt`: the later of the close-out and the completion date's UTC midnight, absent for an order cancelled with neither | `[aircraftUuid, status, completionDate, uuid]`, `[aircraftUuid, closedAt]`, `[aircraftUuid, numberKey]`          |
| Job cards          | `workOrderUuid`; `numberKey`; once closed, `closedAt`: the card's last update, since a closed card takes no more edits                                                                                                                          | `[workOrderUuid]`, `[aircraftUuid, workOrderUuid]` (S3), `[aircraftUuid, closedAt]`, `[aircraftUuid, numberKey]` |
| Archived job cards | `workOrderUuid`; `numberKey`                                                                                                                                                                                                                    | `[workOrderUuid]`, `[aircraftUuid, numberKey]`                                                                   |
| Cost records       | `kind`; a work order's record also `workOrderUuid`                                                                                                                                                                                              | `[programUuid, kind]`, `[workOrderUuid]`                                                                         |
| Parts requests     | `sourceWorkOrderUuid` and `sourceUuid` from the request's source; `numberValue` (the sequence the next number continues)                                                                                                                        | `[sourceWorkOrderUuid]`, `[sourceUuid]`, `[programUuid, numberValue]`                                            |
| Purchase orders    | `numberValue`                                                                                                                                                                                                                                   | `[programUuid, numberValue]`                                                                                     |

Two tables are declared: S3 fills the first, S4 the second. Neither holds records: both are rebuilt from the records, and neither writes the change log.

- `recordNumbers`: every work order and live job card number by aircraft (`aircraftUuid`, `kind`, `key`, `uuid`), indexed by `[aircraftUuid, kind, key]` and by `uuid`. Keyed by aircraft, the numbers move with an aircraft's records.
- `costLedger`: work-order spending by day (`programUuid`, `aircraftUuid`, `workOrderUuid`, `date`, `laborSeconds`, `laborCents`, `partsCents`, `otherCents`), indexed by `[programUuid, aircraftUuid, date]` and by `workOrderUuid`. S4 fills it ([Cost ledger](#cost-ledger-s4)).

Writes that bypassed `encode` now go through it: job-card evidence (`convex/taskCards.ts`), template copies and their progress (`convex/workOrderCopies.ts`), task-file imports (`convex/taskImports.ts`), recurring parts requests (`convex/recurringParts.ts`), purchase-order receipts' request updates (`convex/purchaseOrders.ts`) and the sample program (`convex/sampleProgram.ts`). Flight submissions and reviews (`convex/operations.ts`), the sample program and the load test's generator set `startedAt`. Every flight read decodes the row first (`decodeFlight`), so the column never reaches a screen or a change-log entry.

### Running the backfill

After deploying S2 on a deployment that holds data from before it, and after restoring a backup taken before it:

```bash
npx convex run migrations:backfillHistoryColumns
```

It fills the columns table by table, 100 rows per transaction, writes no change-log row and changes no record. It answers `{ missing, tables }`: how many rows lacked their columns, now filled, in all and by table. Run it again until `missing` is 0. It is safe to rerun and beside live traffic, since every write since S2 sets the columns; a run cut short (an action's 10-minute limit) keeps what it filled, and the next run fills the rest. A payload its schema refuses stops it with "Cannot derive the columns of <table> row <uuid>.", after the pages before it are filled.

### Numbering

A work order or job card save numbers from `recordNumbers` (`convex/recordNumbers.ts`) instead of every record: the rows equal to the number the command or the record names, and those starting with the year's prefix (`workOrderNumberPrefix`, `cardNumberPrefix`). The domain keeps its rules (the first free number, unique ignoring case, live cards only) and takes the numbers as an option; the demo reads its snapshot. `writeChanged` and the direct inserts (template copies, task-file imports, the sample program) write a record's row, and deleting a job card (archiving it with a removed item, or deleting its template) drops it. Parts request and purchase order numbers continue from the highest `numberValue`, which one index row gives; they need no number rows.

### Before deploying S3

Bounded saves find rows by their derived columns, so on a deployment holding rows from before S2, `migrations:backfillHistoryColumns` must report 0 before S3 serves saves. A row without its columns is invisible to them: a work order could close with an open job card that lacks its `workOrderUuid`. Component corrections are the exception, reading orders without a closing time too.

### Rebuilding the number rows

After deploying S3, after restoring any backup, and after loading the load test's generated history:

```bash
npx convex run migrations:rebuildRecordNumbers
```

It writes each work order's and live job card's missing or stale row, then deletes rows no live record holds, 100 rows per transaction, and answers `{ missing, tables }`: rows written or deleted, in all and by table paged (`recordNumbers` counts the deleted). Run it until `missing` is 0; until then a blank number can repeat one an older record holds. It writes no record and no change-log row, and is safe beside live traffic. A payload its schema refuses stops it with "Cannot derive the columns of <table> row <uuid>.".

## Cost ledger (S4)

`costLedger` holds each work order's cost by day for each program that paid (decision D14): labor time and money, parts and other costs. `workOrderLedger` (`src/domain/costs/ledger.ts`) derives the rows by summing `workOrderCosts` per day with stock costs left out, so over any period they sum to the domain's total at the prices the records fix: labor, other costs, and parts at a manual unit cost, else the price recorded at issue (D13). A part priced only by its stock item's current cost, an issue from before D13 with no manual cost, counts nothing: that cost changes without a cost write, so no stored total could follow it. The board, which cannot read stock costs, totalled parts the same way before.

- **Kept in step** (`convex/costLedger.ts`, `syncWorkOrderLedger`) in the transaction of each write that changes a work order's cost: a cost command, a parts issue (through the cost records D13 writes) and a job card joining a work order. A work order save needs none: archiving a card keeps its work order, and a request on it counts the same live or archived. The rows are derived, so they write no change-log row, and an aircraft's transfer leaves them with the program that paid.
- **The board** sums each aircraft's rows of the year (one index range per aircraft) for its quarter, year and budget status, and reads only the budgets of the cost records: no job card, parts request or work-order cost record. At three fleet-years of the size test it reads 2,288 documents and 1.31 MiB, against 6,214 and 11.56 MiB before, and returns the same snapshot. It still grows, by the completed work orders and problem reports it reads, which is the window's to bound (S7).
- **`history.costReport({ aircraftUuid, from, to })`** (`convex/history.ts`) sums an aircraft's rows over a period by work order, with the totals and the aircraft's budgets for the years the period touches. Program administrators only; it refuses an aircraft the caller cannot read with "History not found.", as the other history queries do; the rule is `assertCostReportReader` (`src/domain/costs/costReport.ts`). The Costs screen reads it (S6, below), and the demo builds the same report from its records (`snapshotCostReport`).
- **History's pages** read the cost records, parts requests and purchase orders their visibility rule needs by uuid, as rows name them, as the Weekly summary has since S3. Past 100 records looked up, a page ends short and resumes where it stopped.
- **The nightly reconcile** (`migrations:reconcileCostLedger`, 09:37 UTC) compares every work order's rows with its records and logs the work orders that differ, the first 20 by uuid; it changes nothing.

### Rebuilding the cost ledger

After deploying S4, after restoring any backup, after the reconcile logs a difference, and after loading the load test's generated history:

```bash
npx convex run migrations:rebuildCostLedger
```

It rewrites each work order's rows for every program that paid, then deletes rows whose work order no longer exists, 100 rows per transaction, and answers `{ missing, tables }`: rows written or deleted, in all and by table paged (`costLedger` counts the deleted). Run it until `missing` is 0; until then the board can show less than was spent. It writes no record and no change-log row, and is safe beside live traffic.

## Paged queries (S5)

`convex/history.ts` holds the queries, `Backend` the methods (`historyPage`, `workOrderHistory`, `flightsInRange`), and `src/data/demoHistory.ts` the demo's, which scopes its full snapshot and runs the same domain functions. The screens call them from S6.

| Query                                                   | Returns                                                                                                                                         |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `history.flights` (`aircraftUuid?`, `status?`)          | The next page of older flights, and the pilots and copilots they name                                                                           |
| `history.discrepancies` (`aircraftUuid?`)               | The next page of older problem reports, and the reporters and resolvers they name                                                               |
| `history.workOrders` (`aircraftUuid?`)                  | The next page of older work orders, each with its job cards, archived job cards (which page with their order, per S0) and cost record           |
| `history.workOrder` (`uuid`)                            | One work order, in the window or not, with its job cards, archived job cards, costs, evidence, files and parts requests (`workOrderHistory`)    |
| `history.flightsInRange` (`aircraftUuid`, `from`, `to`) | One aircraft's flights started in `[from, to)`, newest first, with their pilots; more than 1,000 is refused, so a longer span is asked in parts |

The list queries take `{ programUuid, aircraftUuid?, cursor, numItems }` and answer `{ records, members, isDone, continueCursor }`, as `historyPage` does.

- **Checks.** Each query calls `checkContext` first, which refuses a session-less caller, a stale program, aircraft owners and board members. Only aircraft passing `can(state, a, "read")` are read, and any other `aircraftUuid` or work order is refused with "History not found.", the same as one that does not exist. Rows come back through `scopedSnapshot`, so a non-administrator's costs lose their rates and other costs as in the workspace. A work order's cost records are read only for the active program, which paid (D14).
- **Reads.** A list reads one index range per readable aircraft (two for work orders: completed and cancelled), from the later of the cursor and the list's start (`historyStart`), merged by position (`convex/historyScan.ts`). A work order the window keeps on its own fields costs no further reads; one that may be older brings its job cards and costs, by work order. A request stops at a quarter of Convex's limits (1,000 index ranges or 4 MiB), returning a short page that is not done, whose cursor resumes where it stopped.
- **Equal to the oracle.** Short of that budget, a page equals `historyPage` on the caller's scoped snapshot, cursor included: `convex/history.test.ts` checks it for an administrator, a one-aircraft pilot and a mechanic at several page sizes, and `convex/historyVolume.test.ts` on two fleet-years of the size test's program, where the window and the pages together hold every record once.
- **Columns first.** A list or range over flights or work orders still missing their derived columns is refused with "History columns are missing on …; run migrations:backfillHistoryColumns." rather than skipping those rows.
- **Members.** A page loads the users its rows name and keeps those the workspace's rule keeps for those rows: the caller, active members of the program, and the pilots and copilots of the page's own flights. The full-history snapshot also names a former member who flew any flight, so it can name a former member who reported or resolved an older report when a page cannot (pinned in `convex/history.test.ts`).

## Screens and features (S6)

Two data modules read the S5 queries for the browser; nothing else calls them, so every older record still passes the server's checks and `scopedSnapshot`.

- `src/data/historyPages.ts`: `useHistoryPages` pages one list for a screen, a page at a time while connected. Pages live in memory only: a change of user, program or list filter drops them, and a new change-log entry of the list's kind (`flight.`, `discrepancy.`, or `workOrder.`, `taskCard.`, `labor.` and `cost.` for work orders) reloads as many pages as were loaded, since pages are not reactive. `withHistory` joins loaded rows to the snapshot by uuid, the snapshot's copy winning. `HistoryRecordsContext` carries a screen's joined records to the components under it (`useRecordsSnapshot`), and `useWorkOrderHistory` loads one older work order whole.
- `src/data/historyLoads.ts`: whole-history reads for features that need every record: an aircraft's lists to the end with older orders' files, named work orders, flights over a span (asked in halves when the server refuses one as too long), closed work orders back to a date, and one month.
- `src/components/HistoryPager.tsx`: "Showing the last 3 months · Load older" under a list (6 months for flights, `historyWindowMonths`), ending "· All records loaded" once nothing older is left. Offline the button is disabled, with "Older records need a connection". Change history and record history use it too, in place of Load more.

## Lookups by uuid the window can break

Every place, in `src/`, `convex/` and `scripts/` (tests excluded), that finds a flight, problem report, work order, job card, archived job card or cost record by its uuid, or by a uuid that refers to one, in the workspace snapshot or in a load of full history. Found by reading each of the 278 references to those six collections and the reference fields that point at them (`workOrderUuid`, `flightUuid`, `discrepancyUuid`, `taskCardUuid`, `linkedUuid`), then the callers of each helper.

**The real count is 134 sites in 48 files.** 42 of them, in 24 files, need work (41 to load on demand, 1 to refuse) and 92 are not affected. Two number allocations break the same way, by number rather than uuid. The plan estimated 85 sites in 42 files.

What should happen:

- **Load on demand:** the record can legitimately be older than the window. In the browser it comes from the paged queries (S5) before use; in a save, S3's bounded load reads it by uuid.
- **Refuse:** proceeding without the record could let through something unsafe, so the command is refused until the record is loaded.
- **Not affected:** the record looked up is always in the window when the lookup runs.

One assumption holds throughout: a record a screen shows from a history page is merged into what that screen reads, with the job cards, archived job cards and cost record its page carries. The risk is a lookup that starts from another record or a link.

## Where the code differs from the plan

- **Archived job cards have no screen of their own.** They show only in a work order's "Removed items" (`src/components/WorkOrders.tsx:1956`), so they page with their work order, as `historyPage` does, rather than through a "Load older" of their own. The Job cards screen, which does list every card, is missing from the plan's five screens.
- **No record carries a "changed at" time.** Work orders, flights and job card links have no single update time; a reviewed flight records no review time, and a part's unit cost no time at all. "Changed within the window" is read from the dated events each record does hold, listed above.
- **`historyPage` takes `now`**, like `retainedSnapshot`, since the pages are whatever the window leaves out at that moment.
- **Index ranges do not grow with history.** The snapshot reads a fixed number of index ranges (1,011 for an administrator at any size); bytes are what history pushes past the limit.
- **`costLedger` stays with the program that paid.** The plan keys both new tables by aircraft so they move with transfers, but cost records stopped moving with an aircraft on 19 Nov (decision D14, AC-10). A ledger that moved would show the destination's board money it never spent, so its rows carry `programUuid`, which its index starts with. `recordNumbers` is keyed by aircraft, as planned.
- **An archived job card has no `archivedAt`.** A card is archived unchanged, and only its work order dates the removal (`archivedTasks[].removedAt`), so the card has no archive time to copy. It pages with its work order, which needs only `workOrderUuid`.
- **Later events on a closed work order have no column.** The window keeps a closed order revised, corrected or with an item removed in the last 90 days, but `closedAt` dates only the closing. S7 needs another derived column for those events (another backfill), or such an order drops out of the workspace.
- **Paging follows the indexes, not the screens' current sort.** S1 paged flights by start time as recorded and work orders by opening time, neither of which an index serves. S5 changed the oracle to the indexed orders above; the Flight log and Work orders screens followed in S6.
- **The window is judged on the caller's scoped records.** `historyPage` and `retainedSnapshot` run on a scoped snapshot, and a non-administrator's cost records lose their other costs, so a closed work order whose only change in the window is an other cost is older history for a mechanic and kept for an administrator. The server matches it by judging each order on its scoped job cards and costs. S7 must compute the workspace's window the same way, or page and window could disagree for a non-administrator.
- **Parts requests and purchase orders still load whole in their own saves (S3).** H5 keeps them complete, and those saves read them for request ids, open repairs and purchase allocations, which no index covers. Bounded otherwise, the two saves grow by the requests and orders a year adds: about 0.4 MiB a year at the size test's volume, about 8.5 MiB at 20 years, inside Convex's 16 MiB but not the plan's four times headroom. Paging them waits on H5.
- **`recordNumbers` numbers work orders and job cards only.** Parts request and purchase order numbers continue from the highest number, which S2's `[programUuid, numberValue]` index gives in one row; a table would add writes and nothing else. The plan's numbering for all four needs it only for the first two.
- **`recordNumbers` overlaps S2's `numberKey` indexes.** `[aircraftUuid, numberKey]` on work orders and job cards could check one number's uniqueness, but the next free number scans a year's numbers, and Convex reads whole documents: a year of job cards is about 1,000 documents, against 1,000 small number rows.
- **S3 adds an index.** S2 indexed job cards by `[workOrderUuid]` alone, which finds the cards on no work order of every program; `[aircraftUuid, workOrderUuid]` finds an aircraft's.
- **Saves need S2's backfill finished.** The plan runs it after S2; if S2 and S3 deploy together, saves must wait for it ([Before deploying S3](#before-deploying-s3)).
- **A correction refuses past 200 later close-outs, and the Weekly summary past 100 looked-up records.** Both are bounds the plan did not set; each refuses or reports the period cut short rather than read without limit.
- **The AD save is bounded too.** The brief listed seven saves; the lookup table above lists the AD save's work order check with them.
- **The ledger cannot price issues from before D13 at the stock's current cost (S4).** D13 kept those issues on the current cost, which moves without a cost write, so the ledger counts them as unpriced, as the board always has. Since S6 the Costs screen and its budget bar read the ledger too, so such an issue counts nothing there either; recording a price on it, an audited correction, makes it count everywhere.
- **The board now counts every request of the paying program on an order.** It totalled only the requests it could read, those of its aircraft; a request on no aircraft, such as a stock request a work order names, counted on the Costs screen but not on the board. The ledger counts it on both. The volume fixture has none, so the board's snapshot is unchanged.
- **The work order save writes no ledger rows.** The brief named it for archived and linked cards, but archiving keeps a card's work order and a work order save links no existing card; a job card joining an order (`taskCards.save`) writes them.
- **Board budgets and cost settings read rows written before the `kind` column too.** `budgetAndSettingsDocs` (`convex/workingSet.ts`) adds one range for rows the backfill has not filled, so a budget is never missed before it runs.
- **`history.costReport` joins the paged queries in `convex/history.ts`.** S4 and S5 each added the file; the merge keeps one module with one pattern: `checkContext` first, then "History not found." for an aircraft or record the caller cannot read.
