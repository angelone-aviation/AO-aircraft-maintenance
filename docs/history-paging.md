# History paging

The workspace keeps a retention window of history; older flights, problem reports and work orders load page by page ([ADR-0013](adr/0013-history-retention-window.md), decision D3, finding SZ-1). This page holds the window's rule, the read counts it is measured against, and every lookup by uuid the window can break, with what each one should do.

Status, 20 Nov 2026: the rule exists in the domain and is tested (`src/domain/retention.ts`), the baseline is recorded (`convex/historyCost.test.ts`), and every row the window will index carries its derived columns, with a backfill for older rows (S2, below). Nothing reads the columns or calls the rule yet; the workspace still loads full history.

## The window

`retainedSnapshot(snapshot, now)` keeps, from a full scoped snapshot:

| Records                       | Kept in the workspace                                                                                                                                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Flights                       | Held for review, or started or submitted in the last 183 days (`FLIGHT_RETENTION_DAYS`, H1)                                                                                                                              |
| Problem reports               | Open (deferred ones included), or created, resolved or deferred in the last 90 days (`RETENTION_DAYS`)                                                                                                                   |
| Work orders                   | Open; holding an open job card; opened, closed, revised, corrected, or with a job card or cost entry changed in the last 90 days; or among the 5 latest completed on their aircraft, ties kept (the owner portal's list) |
| Job cards, archived job cards | With their work order; templates and cards of an order not in the snapshot always                                                                                                                                        |
| Cost records                  | A work order's with its order; budgets and the labor rate always                                                                                                                                                         |
| Everything else               | Complete: inspections, ADs, management records, checklists, templates, parts requests, purchase orders and flight plans (H5); the change log keeps its 250 rows                                                          |

The cutoff is the start of the UTC day the window opens on (`retentionCutoff`). Rounding down only widens the window and holds one cutoff for a whole day, so a record crossing it appears both in an older copy of the workspace and in the newer history pages, never in neither.

`historyPage(snapshot, request, now)` is the paging oracle: the next page of what the window leaves out, for flights (optionally one aircraft and one status, H2), problem reports or work orders, newest first in the order below. A work order page carries the order's job cards, archived job cards and cost record, and every page the members its rows name (pilots, copilots, reporters and resolvers) for their names. The cursor is a position (sort key and uuid), not an offset, so it stays valid when newer records arrive. An aircraft the snapshot does not list is refused with "History not found.", as one that does not exist. The demo pages with it, and the server's paged queries are tested against it.

### The order of each list

Each list's order is one index range per aircraft on the server, so a page reads only the rows it returns and the rows the window keeps between them (S5 resolved correction 4 this way, changing the oracle rather than adding a column):

| List            | Newest first by                                                        | Index range per readable aircraft                                                 |
| --------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Flights         | Start instant (`startedAt`)                                            | `started`: `[aircraftUuid, startedAt, uuid]`, below the flight cutoff             |
| Problem reports | Creation time                                                          | `status`: `[aircraftUuid, status, createdAt, uuid]`, resolved only                |
| Work orders     | Completion date; a cancelled order without one after every dated order | `status`: `[aircraftUuid, status, completionDate, uuid]`, completed and cancelled |

- **Equal keys by uuid, highest first.** The three indexes end in `uuid`, so the server reads ties in the oracle's order and a cursor resumes inside a tie. Convex otherwise breaks ties by creation time, which a demo or a backup restore cannot reproduce. Adding a field to an index needs no backfill: Convex builds the index from stored fields.
- **Flights by instant, not by the recorded text.** The text keeps the pilot's offset, so it does not sort by instant across offsets; `startedAt` is that text in milliseconds. The Flight log sorts by the text today, which is the same order whenever a program's flights share an offset; S6 sorts it by instant.
- **Work orders by completion date, not opening.** No column holds `recordedAt`, and one would need another backfill. Every order the window leaves out is closed, so its history is closed work, which the owner portal and the paper check already list by completion date. Completed orders always have one; a cancelled order may not (""), and sorts last. `closedAt` was the other candidate, but it is absent on every open order and on a cancelled order without dates, so its range would mix open orders into history; the `status` index never reads an open order. The Work orders screen sorts by opening today; S6 lists closed orders by completion date, under the open ones.
- **No older row sorts before its list's start** (`historyStart`): a flight started, report created or order completed on or after the cutoff's day is never older history, so each range starts there.

## Derived columns and tables (S2)

The window's queries need indexes on fields that live inside a record's JSON payload, so each row copies those fields into columns of its own. `encode` in `convex/collections.ts` sets them on every write of a payload row, and `flightColumns` on every write of a flight's start; decoding never returns them, so the workspace, the change log and the readable records copy are unchanged. Every column is optional, so rows written before S2 stay valid until the backfill fills them. Nothing reads a column or a new table until S3.

| Table              | Derived columns                                                                                                                                                                                                                                 | New indexes                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Flights            | `startedAt`: the start time in milliseconds, since the stored text keeps the pilot's offset and does not sort by instant                                                                                                                        | `[aircraftUuid, startedAt]`, `[aircraftUuid, submittedAt]`, `[aircraftUuid, status]`              |
| Problem reports    | None: the fields are columns already                                                                                                                                                                                                            | `[aircraftUuid, status, createdAt]`, `[aircraftUuid, resolvedAt]`                                 |
| Work orders        | `status`; `completionDate`; `numberKey` (the number in lower case, as the uniqueness check compares it); once closed, `closedAt`: the later of the close-out and the completion date's UTC midnight, absent for an order cancelled with neither | `[aircraftUuid, status, completionDate]`, `[aircraftUuid, closedAt]`, `[aircraftUuid, numberKey]` |
| Job cards          | `workOrderUuid`; `numberKey`; once closed, `closedAt`: the card's last update, since a closed card takes no more edits                                                                                                                          | `[workOrderUuid]`, `[aircraftUuid, closedAt]`, `[aircraftUuid, numberKey]`                        |
| Archived job cards | `workOrderUuid`; `numberKey`                                                                                                                                                                                                                    | `[workOrderUuid]`, `[aircraftUuid, numberKey]`                                                    |
| Cost records       | `kind`; a work order's record also `workOrderUuid`                                                                                                                                                                                              | `[programUuid, kind]`, `[workOrderUuid]`                                                          |
| Parts requests     | `sourceWorkOrderUuid` and `sourceUuid` from the request's source; `numberValue` (the sequence the next number continues)                                                                                                                        | `[sourceWorkOrderUuid]`, `[sourceUuid]`, `[programUuid, numberValue]`                             |
| Purchase orders    | `numberValue`                                                                                                                                                                                                                                   | `[programUuid, numberValue]`                                                                      |

Two tables are declared, empty until S3 and S4 fill them. Neither holds records: both are rebuilt from the records, and neither writes the change log.

- `recordNumbers`: every work order and job card number by aircraft (`aircraftUuid`, `kind`, `key`, `uuid`), indexed by `[aircraftUuid, kind, key]` and by `uuid`. Keyed by aircraft, the numbers move with an aircraft's records.
- `costLedger`: work-order spending by day (`programUuid`, `aircraftUuid`, `workOrderUuid`, `date`, `laborSeconds`, `laborCents`, `partsCents`, `otherCents`), indexed by `[programUuid, aircraftUuid, date]` and by `workOrderUuid`. Where an issued part's price comes from is decision D13's, so S2 assumes nothing about `partsCents`.

Writes that bypassed `encode` now go through it: job-card evidence (`convex/taskCards.ts`), template copies and their progress (`convex/workOrderCopies.ts`), task-file imports (`convex/taskImports.ts`), recurring parts requests (`convex/recurringParts.ts`), purchase-order receipts' request updates (`convex/purchaseOrders.ts`) and the sample program (`convex/sampleProgram.ts`). Flight submissions and reviews (`convex/operations.ts`), the sample program and the load test's generator set `startedAt`. Every flight read decodes the row first (`decodeFlight`), so the column never reaches a screen or a change-log entry.

### Running the backfill

After deploying S2 on a deployment that holds data from before it, and after restoring a backup taken before it:

```bash
npx convex run migrations:backfillHistoryColumns
```

It fills the columns table by table, 100 rows per transaction, writes no change-log row and changes no record. It answers `{ missing, tables }`: how many rows lacked their columns, now filled, in all and by table. Run it again until `missing` is 0. It is safe to rerun and beside live traffic, since every write since S2 sets the columns; a run cut short (an action's 10-minute limit) keeps what it filled, and the next run fills the rest. A payload its schema refuses stops it with "Cannot derive the columns of <table> row <uuid>.", after the pages before it are filled.

## Lookups by uuid the window can break

Every place, in `src/`, `convex/` and `scripts/` (tests excluded), that finds a flight, problem report, work order, job card, archived job card or cost record by its uuid, or by a uuid that refers to one, in the workspace snapshot or in a load of full history. Found by reading each of the 278 references to those six collections and the reference fields that point at them (`workOrderUuid`, `flightUuid`, `discrepancyUuid`, `taskCardUuid`, `linkedUuid`), then the callers of each helper.

**The real count is 134 sites in 48 files.** 42 of them, in 24 files, need work (41 to load on demand, 1 to refuse) and 92 are not affected. Two number allocations break the same way, by number rather than uuid. The plan estimated 85 sites in 42 files.

What should happen:

- **Load on demand:** the record can legitimately be older than the window. In the browser it comes from the paged queries (S5) before use; in a save, S3's bounded load reads it by uuid.
- **Refuse:** proceeding without the record could let through something unsafe, so the command is refused until the record is loaded.
- **Not affected:** the record looked up is always in the window when the lookup runs.

One assumption holds throughout: a record a screen shows from a history page is merged into what that screen reads, with the job cards, archived job cards and cost record its page carries. The risk is a lookup that starts from another record or a link.

## Where the code differs from the plan

- **Archived job cards have no screen of their own.** They show only in a work order's "Removed items" (`src/components/WorkOrders.tsx:1956`), so they page with their work order, as `historyPage` does, rather than through a "Load older" of their own. The Job cards screen, which does list every card, is missing from the plan's five screens.
- **No record carries a "changed at" time.** Work orders, flights and job card links have no single update time; a reviewed flight records no review time, and a part's unit cost no time at all. "Changed within the window" is read from the dated events each record does hold, listed above.
- **`historyPage` takes `now`**, like `retainedSnapshot`, since the pages are whatever the window leaves out at that moment.
- **Index ranges do not grow with history.** The snapshot reads a fixed number of index ranges (1,011 for an administrator at any size); bytes are what history pushes past the limit.
- **`costLedger` stays with the program that paid.** The plan keys both new tables by aircraft so they move with transfers, but cost records stopped moving with an aircraft on 19 Nov (decision D14, AC-10). A ledger that moved would show the destination's board money it never spent, so its rows carry `programUuid`, which its index starts with. `recordNumbers` is keyed by aircraft, as planned.
- **An archived job card has no `archivedAt`.** A card is archived unchanged, and only its work order dates the removal (`archivedTasks[].removedAt`), so the card has no archive time to copy. It pages with its work order, which needs only `workOrderUuid`.
- **Later events on a closed work order have no column.** The window keeps a closed order revised, corrected or with an item removed in the last 90 days, but `closedAt` dates only the closing. S7 needs another derived column for those events (another backfill), or such an order drops out of the workspace.
- **Paging follows the indexes, not the screens' current sort.** S1 paged flights by start time as recorded and work orders by opening time, neither of which an index serves. S5 changed the oracle to the indexed orders above; the Flight log and Work orders screens follow in S6.
