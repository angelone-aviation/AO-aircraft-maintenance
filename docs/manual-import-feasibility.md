# Maintenance manual import feasibility

Assessed against the local application source on 2026-10-01. This note concerns website capability, not approval of the supplied manual or an aircraft maintenance program. Chapter 5 extraction is a separate artifact; no application records were created by this assessment.

## Conclusion

The website can be extended to upload an aircraft or component manual, extract proposed inspection records, and let the user review and activate selected records. It cannot currently do that. Existing inspection scheduling, component service requirements, linked task cards, storage, and maintenance permissions provide useful foundations. The smallest first release should import aircraft-specific **draft inspection candidates**, rather than introduce the reusable task-template library previously deferred. [Schema](../convex/schema.ts), [task-card scope](./task-cards.md), [inspection commands](../src/domain/management.ts).

## Scheduling and applicability must remain explicit

The current inspection save path requires a last-compliance reading/date for every recurring interval. It calculates next due as baseline plus interval, with calendar intervals ending in the target month. Current aircraft readings are **not** evidence of last compliance and must not be copied into those fields to make an import pass validation. Without maintenance history, keep the candidate awaiting baseline review. Component requirements likewise validate their required baselines. [Inspection save](../src/domain/management.ts), [calendar and due flags](../src/domain/maintenance.ts), [component requirement validation](../src/domain/components.ts).

Multiple supported dimensions already flag due when any limit is reached, which can represent a simple hours-or-months limit. However, the schema has no structured program alternatives, phase sequencing/offsets, initial versus subsequent interval rule, event-triggered requirement, serial-range applicability, modification applicability, or program-specific tolerances. Preserve these source conditions in candidates; do not flatten them into ordinary repeated intervals or activate unsupported rules. A one-time absolute limit is representable, but that is not a general phased-program engine. [Inspection schema and completion behavior](../src/domain/management.ts), [any-limit due behavior](../src/domain/maintenance.ts).

Aircraft records have make/model/serial and the Twin/Turbine/Amphibious flags; serial can be blank. Components have part/serial, installation, position and usage baselines. Those fields help match applicability but do not establish which inspection program the operator uses, modification configuration, or historic compliance. Review for N626KB should therefore capture the serial number, selected program, relevant installed components/configuration and each selected inspection's last completion readings/date. Registration alone is insufficient for those decisions. [Aircraft fields](../src/domain/fleet.ts), [component fields](../src/domain/components.ts).

## Smallest feasible website flow

1. **Aircraft or component → Manuals → Upload PDF.** Store document identity/revision and original file once, scoped to the Flight Program and selected record.
2. **Select chapter/pages → Extract draft candidates.** Show source pages beside proposed titles, references, interval expressions and applicability. Keep complex/ambiguous rules visibly unresolved. A phase/package record and its task rows should remain distinct.
3. **Review applicability.** Select the maintenance program and applicable candidates, match component records, edit extraction mistakes, and retain exclusions with reasons. Show both printed page labels and PDF page numbers.
4. **Enter compliance baselines.** Missing history stays unresolved. For simple supported schedules, preview next due dates/readings using the existing calculators.
5. **Create selected records.** Only reviewed candidates become active inspections/component requirements. Optional task cards start in draft with source-linked instructions and empty execution/signoff fields. Make imports idempotent by document revision, source task, owner and selected program; record who accepted each mapping.

This is a proposed addition, not implemented behavior. The storage, draft-candidate/provenance models and review UI are new work. Existing permission/version/audit patterns and task-card defaults can be reused. Reusable task templates and full support for complex maintenance-program rules can follow separately.
